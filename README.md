# 职场黑话翻译器

贴一句看不懂的工作消息 → **先猜它什么意思** → 揭晓 AI 怎么读，以及**它有多确定**。

> 用的是 [Jev](https://docs.typesafe.ai)（TypeSafe 的 System One 模型）——**不生成文字，只做判断**，
> 每次返回一个类型化的答案 + 一个 0–1 的置信度。所以它能说「这句我也读不懂」。

---

## 为什么有意思：它会在不确定时认输

普通大模型会自信地胡说。这个工具的设计前提恰恰相反——**置信度是主角**：

| 置信度 | 卡片表现 |
|---|---|
| ≥ 0.85 | **斩钉截铁** |
| 0.55 – 0.85 | **它也是猜的** |
| < 0.55 | **这句它也读不懂** |

**「AI 承认读不懂」本身就是它的价值**：它把「模型不确定」和「你的选项里没位置」这两种情况分开暴露出来（见下文「踩过的坑」）。

## 跑起来

零依赖——只用 Python 标准库 + `curl`。前端是单个 HTML。

```bash
git clone https://github.com/casperkwok/heihua-translator.git
cd heihua-translator

# 1) 放 API key（别写进代码）
cp .env.example .env
#    推荐用 Keyward：把值写成 keyward://typesafe-api-key，然后
#    kw exec -f .env -- python3 server.py
#    或者直接填明文 key（.env 已被 gitignore）

# 2) 起服务
set -a; . ./.env; set +a
python3 server.py            # → http://127.0.0.1:8765
```

⚠️ **API key 只在服务端读取，永不进前端**——这是 TypeSafe 明确要求的
（"Keep API credentials server-side in web apps."）。

## 判断设计

一次请求，五个问题并行（同一 state 上的独立问题一起问，官方说加问题几乎不增延迟）：

| 字段 | 原语 | 作用 |
|---|---|---|
| `meaning` | **Choice**（6 类） | 主判断，卡片主角；**置信度取它** |
| `boilerplate` | Score（5 档） | 套话浓度 |
| `has_commitment` | Noul | 有具体可验证的承诺吗 |
| `is_deflecting` | Noul | 在回避或转移吗 |
| `needs_me_to_act` | Noul | 下一步在你手上吗 |

**六类意图**：

| 类别 | 含义 | 典型说法 |
|---|---|---|
| `literal` | 就是字面意思 | — |
| `undecided` | 这事还没定，要再讨论 | 我们先对齐一下 |
| `deferred` | 含糊其辞，实际不会推进 | 这个后面再讨论 |
| `declined` | 在委婉拒绝 | 我建议你再想想 |
| `pushed_back` | 把决定或责任推回给你 | 你自己看着办 |
| `downplayed` | 在轻描淡写，实际更严重 | 这个需求很简单 |

## 踩过的坑（这是本仓库最有价值的部分）

### 坑 1 · 用自己编的句子测，测的是自己

第一版做出来，我用自己编的六句话测——**五句确定度 ≥0.97**，挺得意。

然后我停了一下：**这些句子是我写的，而且是照着我设计的六个类别编的。**
用自己编的题考自己设计的分类，**那测的是「我的分类学跟我自己一致」，不是「它读不读得懂中文」**。

### 坑 2 · 换成真实语料，确定度中位从 0.97 掉到 0.49

换上 [`bench/cases.json`](bench/cases.json) 里的 **30 句真实职场黑话**（句子和它们的真实意思都来自网上的公开整理，**不是我写的**）：

| | |
|---|---|
| 确定度中位 | **0.49** |
| 它说「读不懂」 | **18 / 30** |
| 它很确定 | 5 / 30 |

### 坑 3 · 低确定度的「字面意思」，是求救信号

它答「就是字面意思」的 7 句里，有 5 句确定度低得可疑：

| 它读作 | 确定度 | 真实意思是 |
|---|---|---|
| 帮忙盯一下 | `literal` 0.42 | 烂摊子甩给你 |
| 我对事不对人 | `literal` 0.36 | **就是针对你** |
| 优化组织结构 | `literal` 0.26 | **准备裁员** |
| 按公司规章制度来 | `literal` 0.20 | 公司不允许 |
| 你很有潜力 | `literal` **0.18** | **现在能力还不行** |

**这不是「答对了但不自信」**——它知道话里有话，**但六个类别里没有位置放「表面肯定、实际否定」这种话**，只好退回兜底选项。

### 教训

> **模型说「我不确定」时，有两种可能，长得一模一样：**
> **① 这句话本身就模糊　② 你的选项里没有位置。**
>
> **看它挤向哪里就能分辨**——一堆句子挤在同一个兜底选项上、且确定度都低，**那是分类学的锅，不是模型的**。

这个坑我犯了两次：第一版把「这个需求很简单」塞进 `pushed_back`（确定度 0.36），补一个 `downplayed` 类别后 → **1.00**。模型一个字没改。

## 仓库结构

```
├── server.py            后端（标准库 HTTP + curl 调上游）
├── web/index.html       前端单页（原生 JS，无框架）
└── bench/
    ├── cases.json       30 句真实职场黑话（句子与真实意思均来自公开整理）
    ├── run.py           跑分脚本，输出确定度分布与逐条对照
    ├── result.json      跑分结果
    └── README.md        语料来源与「这不是我的判断」说明
```

## 已知限制

- **中文是 Jev 的弱项**（官方文档自述 "handled but not equally well"；我们另一组实测中文 30/30，两边矛盾）。目前靠**低置信度时自己认输**兜住
- **单句判断依赖语境**——`context` 字段可选，但会明显影响准确率
- **六类分类学是实测归纳的，不是穷举**——仍可能有遗漏
- **置信度三档的 0.85 / 0.55 是拍的**，没有用数据标定过
- 未做并发（`http.server` 单线程），未部署

## 数据与合规

- 判断由 TypeSafe 的 Jev 完成，**请求会发到 `api.typesafe.ai`**——别往里贴不该外发的内容
- 本仓库的 30 句语料来自公开的职场黑话整理，用于评测，**不代表任何具体公司或个人的真实对话**
